### Process ownership and cancellation

Use a small private Windows Job Object owner in the SDK rather than a new orchestration library. UE's general CreateProc (`WindowsPlatformProcess.cpp:530–700`) starts immediately without a caller-supplied Job Object. `TerminateProc(..., true)` recursively snapshots PIDs (`:751–814`), which is not a continuous descendant-ownership guarantee. UE ExecProcess's job object (`:1080–1095,1170`) is process-global and assigned after launch; it is not the per-run owner required here.

Create the worker suspended, assign it to a new native Job Object with kill-on-last-handle-close and no breakaway flags, then resume. On any assignment/resume failure, terminate and wait for only that newly created suspended process; do not fallback to an uncontained launch. Restrict inherited handles to cancellation, parent lifetime/handshake control and any deliberate lease duplicate; the job-object handle itself must not be inherited. UAT/cook/ShaderCompileWorker descendants then inherit containment by the normal Windows process rules. Use the already implemented engine FSerializedUATProcess inside that tree for command generation/output lifecycle, retaining it until its monitor thread drains. SDK root containment supplies the stronger safety boundary. Account for nested Job Objects and deliberately test AutomationTool's actual child process behavior on this machine.

Normal cancellation sets a separate native event and a durable CancelRequested state. The child observes it on readiness/game-thread batch boundaries and during archive I/O; a blocked monolithic package-copy call is not claimed immediately interruptible. Stop creating new phases. After a documented grace period, terminate only the owned job tree. Wait for the worker handle to signal and query JobObjectBasicAccountingInformation until ActiveProcesses is zero; a job-object wait signal alone is not an all-processes-empty test. Do not release the lease or report safely cancelled merely on `OnCanceled`, a log line, heartbeat loss or elapsed timeout. If confirmed drain fails, retain the busy/recovery state and handles; do not start another job.

Parent shutdown removes game-thread callbacks, signals cancellation, joins all module-owned threads and drains the tree before teardown. Parent crash closes its non-inherited kill-on-close job handle. Recovery uses the durable run record plus native PID/start-time/job identity to distinguish a still-live owned process from PID reuse, waits for verified emptiness and never steals a lock by age. Reacquiring the current Workspace lock alone is not enough: it can disappear as the old parent exits while descendant termination is still pending. Root should add the minimal worker lease-transfer/held-lease seam, with the same exclusive file object retained across parent/worker handoff; no release/reacquire window and no second nested acquisition. This first global lease conservatively excludes overlapping host work, satisfying the stronger one-uploader rule; per-avatar state still records the selected LocalAvatarId and exact authoring inputs.

Native basis: [Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) describes descendant association, breakaway and kill-on-close; [AssignProcessToJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject) documents actual assignment failure/nested-job constraints; [QueryInformationJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-queryinformationjobobject) supplies accounting. These are design inputs, not runtime evidence of our toolchain containment.

### Actual supervisor contract and acceptance

The released `AvatarStudioWorkerProcess.h` provides `Launch`, `RequestCancel(GraceMilliseconds<=30000)`, nonblocking `Poll`, bounded `WaitForDrain`, `GetIdentity`, and bounded `TakeOutput`, all on one owned off-game-thread thread. Its actual identity is native PID plus FILETIME. The job name is `Local\\ConvaiAvatarStudio_<hostdigits>_<jobdigits>` and cancellation event is that name plus `.Cancel`. Launch adds the reserved `-AvatarStudioCancelEvent=<name>` itself and rejects a caller override. Only stdout/stderr and NUL stdin are inherited; there is **no inherited cancellation handle, credential pipe or lease transfer in this slice**. The child opens the expected named event with SYNCHRONIZE only. It never opens/retains the kill-on-close Job Object handle.

The host starts its input monitor before fingerprinting, retains the monitor and exclusive lease, writes the request, launches, records actual identity, then compares the first status to `GetIdentity()` and the exact request/profile. Only then does it write accept. The child checks its native current PID/creation time, expected project and cancellation event name, opens the declared supervisor with query-limited/synchronize rights, verifies its native creation time, and waits for the exact accept while observing parent liveness/cancellation. No package write/cook starts before acceptance. Parent death, wrong accept or bounded startup deadline stops the child; it does not guess authorization from a file name.

Phases are monotonic: `ReadyForAcceptance → CheckingPrepared → PreparingCookInputs → Cooking → Archiving? → Verifying → Stopping → terminal result`. Before readiness the parent owns `Launching`; it is not a forged child phase.
